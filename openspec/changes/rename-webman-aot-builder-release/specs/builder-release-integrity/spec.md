## Purpose

定义新名称首次发布时的资产一致性与验证要求，确保公开版本、锁定组件、安装包、摘要、更新来源和跨平台构建证据可以相互核对，避免历史资产被误改或误用。

## ADDED Requirements

### Requirement: 发布版本与资产一致
发布者 SHALL 先核对远端已有标签和资产，再选择未占用的下一版本；该版本的 Mac 与 Windows 轻量包、完整包、精简组件、发布说明、锁文件和摘要 SHALL 使用一致的新版名称及版本。

#### Scenario: 版本已被占用
- **WHEN** 候选版本标签或发布资产已存在
- **THEN** 发布流程停止复用该版本，并在重新确定版本后同步所有版本字段与资产名

#### Scenario: 用户下载资产
- **WHEN** 用户从新仓库 Release 下载新版本包
- **THEN** 文件名、包内命令、安装后版本输出和校验摘要对应同一个版本

### Requirement: 组件来源与摘要可验证
新版本组件 SHALL 由锁定输入重建，或在验证内容、可重封装范围和名称变更影响后重新封装；锁中的组件摘要、清单摘要、工具链指纹与发布摘要 SHALL 对应实际文件。

#### Scenario: 安装完整包
- **WHEN** 用户离线安装完整包
- **THEN** 安装器完成内置组件校验和准备，不访问旧版用户缓存，也不依赖下载新版组件

#### Scenario: 首次使用轻量包
- **WHEN** 用户首次执行新版轻量包的 `doctor` 或 `build`
- **THEN** 下载来源为新版本资产，组件在使用前按新锁验证；摘要或清单不符时明确失败且不采用该组件

### Requirement: 更新路径不跨越命名迁移
新版若宣称 `self-update` 可用，SHALL 提供指向新仓库的真实 HTTPS 签名 manifest 和受信公钥，并仅在新版安装状态内完成已验证的升级与回退；旧版自更新 SHALL NOT 冒充完整的改名安装流程。缺少更新配置或受信公钥时，发布说明 SHALL 明确自更新未启用，不得宣称自动更新源可用。

#### Scenario: 新版自更新
- **WHEN** 发布者宣称已安装新版支持 `self-update`
- **THEN** 实际命令从新仓库的签名 manifest 验证目标包，并在新用户目录完成升级与回退

#### Scenario: 缺少更新源或受信公钥
- **WHEN** 发布候选没有可用的 manifest URL 或受信公钥
- **THEN** 自更新验收保持未完成，发布说明不得宣称自动更新源可用，命令明确报告缺失配置

#### Scenario: 旧版尝试升级到新名称
- **WHEN** 旧版命令只更新其应用载荷
- **THEN** 用户不会被告知新命令或新用户目录已经安装；须使用新版安装器完成迁移

### Requirement: 发布前平台验收
发布者 SHALL 验证 Mac 与 Windows 的轻量包和完整包安装、命令、组件准备、构建与卸载，并验证对应 Linux amd64 产物的静态属性及项目业务路径；未通过的适用平台不得宣称已验收或发布完成。

#### Scenario: 一个平台缺少实跑证据
- **WHEN** 只有另一平台或仅有静态检查证据
- **THEN** 发布记录明确该平台未通过验收，发布门槛保持未满足

#### Scenario: 两平台候选固定
- **WHEN** 两平台候选使用相同锁定输入且均完成规定验收
- **THEN** 发布记录保存候选、摘要、实际入口、关键步骤与结果，可复核发布资产
