## Context

参见 [proposal.md](proposal.md) 的动机。当前源码版本是 `0.1.3`；已发布包与大量源码位置仍使用 `webman-aot`。上一轮在当前分支留下未提交的命令与安装包改名候选，其语义偏向保留旧入口；本次须在核对差异后继续改为完整新身份。现行用户目录由 `src/Platform/UserDirectoryLayout.php` 决定，精简组件锁含旧名、版本、组件及清单摘要，安装包由 `tools/package-installers.php` 生成。自更新只替换 CLI 应用载荷，无法自动新增全新的命令入口。

## Goals / Non-Goals

**Goals:**

- 使新版本的所有自有公开标识、磁盘状态和构包结果使用同一个产品名；旧资产与旧状态可清晰识别。
- 在构包前建立版本、组件、签名与摘要的可追溯关系；按平台证据决定能否发布。
- 让首次用户与旧版用户都能照新文档走通安装、构建、验证与卸载路径。

**Non-Goals:**

- 改动已经发布的 v0.1.3 文件、标签或资产内容。
- 自动迁移或删除旧版用户目录及缓存。
- 修改 Webman 项目和 TypePHP 上游第三方身份，或改变 Linux 程序的运行模型。

## Decisions

### 全量替换自有身份，保留历史和上游事实

把自有 PHP 命名空间、类引用、CLI 文件、环境变量、用户目录、项目缓存键、schema、诊断与生成物身份统一改为新名，避免两个并行命名体系长期存在。批量替换前先按源码、锁、安装器、文档、历史证据及第三方引用分类，逐处核对；历史 v0.1.3 描述和第三方出处保留准确原名。与仅新增 CLI 别名相比，这符合“所有相关的一切都改名”，但会产生刻意的命令、变量和缓存断点。

### 新安装器拥有独立状态根

Mac 使用 `~/Library/Application Support/webman-aot-builder`，Windows 使用 `%LOCALAPPDATA%\webman-aot-builder`；新环境变量覆盖根目录。新安装器、卸载器和自更新只作用于新根。旧版目录不直接复制或读取为有效缓存；需要重用组件时只能经过锁和内容校验后作为新组件输入。相比原地迁移，此法可避免旧缓存格式、哈希和版本状态被新版误信任，也允许旧版与新版并存。文档提供有序手动切换步骤。

### 组件须以新身份产生可验证锁

从锁定输入重新构建 Mac/Windows 精简组件；如选择重封装现有组件，先检查内容路径、清单、内部名称、工具链指纹和复现性，并记录证明重封装等价的证据。实际归档与清单重新求 SHA-256，更新相应锁、包摘要及更新清单；绝不只改文件名却沿用旧摘要。签名验证继续使用既有受信机制，更新源改至新仓库。旧版 `self-update` 不承担迁移职责，新安装包是新命令的交付入口。

当前 `self-update` 未配置默认 manifest URL，仓库也没有 `update-trusted-keys.json`。无参数命令会报告 URL 未配置；即使显式提供 URL，缺受信公钥仍不能完成签名校验。因此不能仅靠改仓库 URL 或 schema 就声称 v0.2.0 自动更新可用。若将自更新纳入本版可用范围，须准备由实际受信私钥签发的 manifest、相应公钥、指向新仓库的 HTTPS URL，并在新用户根内实测升级与回退；不得生成虚构密钥或只用模拟签名代替发布链。条件不满足时在任务与发布说明中明列为未完成。

### Mac 运行时字节必须重新固定

`installer/runtime.lock.json` 锁定已签名 Mac PHP CLI 与 compiler driver 的二进制 SHA-256。`tools/sanitize-macos-cli-runtime.php` 的签名 identifier `org.webman-aot.cli-php` 及构建路径前缀、`tools/build-macos-compiler-driver.sh` 的编译前缀仍含旧名，这些值影响最终字节。完整改名须先更新这些输入，从锁定源码重新构建并验证 Mac PHP CLI 和 compiler driver，再以实际二进制重新计算并写入锁文件 SHA；仅替换 schema 或沿用旧二进制指纹不能视作完成或发布候选通过。

### 跨宿主一致性以新候选实测为准

`tools/windows-replay.ps1` 的 `expectedMacArtifactSha256` 与 `expectedNormalizedInputSha256` 属旧构建证据；`tools/build-full-static-smoke.php` 的新 reproducible source prefix 已改变构建输入及产物。完成新身份构建后，须在 Mac 与 Windows 分别重跑同一锁定输入的完整静态 smoke，取得实际输入及 Linux 产物摘要，核对一致性后再刷新 replay 的预期摘要。旧摘要可保留为历史参照，不能用于宣称本次跨宿主一致或通过发布验收。

### 远端发布按固定候选推进

先读远端当前仓库、标签、Release 和 CI 状态，确认目标 v0.2.0 尚可用；若已占用，选下一个未占用版本并同步全部字段。先在 feature branch 完成源码、两平台组件和四种安装包，记录摘要与平台验证；经过独立发布候选审查后执行仓库改名、推送、打 tag、创建 Release、上传资产和发布页复核。GitHub 原地址可能重定向，但新文档和更新源直接使用新地址，不以重定向作为正确性证据。

## Risks / Trade-offs

- [旧版用户误以为自更新完成迁移] → 新版文档和旧版可到达的说明明确安装新包与新命令验证步骤。
- [旧目录或旧变量污染新版本] → 新根与新变量独立，候选安装时用预置旧状态测试隔离。
- [组件重命名后锁与实际文件不符] → 两平台归档、清单、锁及安装时摘要逐级核对；不匹配立即失败。
- [Mac 已签名运行时仍含旧身份或字节变化后沿用旧摘要] → 重新构建、检查签名 identifier 与路径前缀、验证可执行文件，并以实测 SHA 更新锁；旧摘要可暂留在未完成候选中，但不得据此构包或发布。
- [跨宿主比较沿用旧构建摘要] → Mac 和 Windows 用新 prefix 分别实跑，核对实测输入与产物摘要后更新 replay 期望值；缺一平台时不宣称一致。
- [自更新源码具备校验逻辑却缺真实更新源与公钥] → 将默认 manifest URL、真实签名 manifest、受信公钥及新根升级回退分别验收；缺项时保留未完成并在发布说明中写明。
- [组件和远端证据当前不可得] → 当前本机缺少两平台精简组件 ZIP，且 GitHub DNS 与 `gh` 认证失效；恢复下载/认证后核对实际资产和版本，不能把旧锁或预期文件名当作实物证据。
- [仓库更名影响旧链接和更新] → 发布前审计所有自有 URL、CI、签名清单与安装说明，并实际下载验证新地址。
- [平台或 Linux 业务验收缺失] → 保留明确未通过项，不把静态检查或另一平台结果记作该平台通过。

## Migration Plan

1. 固定当前未提交改名候选的差异，核对远端版本、组件来源和所有旧名用法。
2. 实现新身份、新安装根和源码/包/文档一致性；在隔离目录先构建、安装和测试。
3. 重新构建并校验 Mac PHP CLI 与 compiler driver 的新身份二进制，更新真实 SHA；取得并校验两平台精简组件，重新生成组件锁和安装资产，固定候选、摘要、更新签名及审查结论。
4. 完成 Mac、Windows 和 Linux 目标路径验收后，改 GitHub 仓库名，推送、打 tag 并发布新资产；核对新仓库、下载、安装和更新链。
5. 若发布前失败，仅修候选并重验；若远端发布后发现缺陷，停止推广新包，以新的修订版本修复。保留历史 v0.1.3 资产和旧目录，避免回滚时破坏既有用户状态。
